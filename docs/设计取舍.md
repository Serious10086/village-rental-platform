## 交易域

- **锁的顺序决定成败**:`FOR UPDATE` 必须在**校验之前**获取。先校验再加锁
  等于没加锁 —— 校验用的是加锁前的旧数据,两个并发请求会双双通过
  "没有冲突"的检查,然后各自插入订单。这就是典型的
  **检查后使用(TOCTOU)** 竞态。
- **`UPDATE balance = balance + ?` 而不是"查出来加完再写回"**:
  后者在并发下会丢更新 —— 两个请求都读到 100,各自写回 150,总入账
  只有 100。加法必须在数据库端、在行锁保护下完成。
- **租赁和出售必须分开处理资源状态**:租赁被占用的是"某一段日期"
  而不是资源本身,把有订单的租赁资源整体锁住,发布者一个月就只能
  做一单生意。出售是一台机器只有一个,下单就得先锁住。
- **区间重叠判定用 `已有.开始 <= 新.结束 AND 已有.结束 >= 新.开始`**,
  不能写成"完全包含" —— 用户问"下周能租吗",只要资源下周有一部分
  空闲就该算可租。
- **租期天数含头含尾**:`ChronoUnit.DAYS.between` 算的是"隔了几天",
  9/1 到 9/3 得到 2 而不是 3。这个差 1 很容易漏,漏了就是每天少收一天租金。
- **金额永远在服务端算**:下单接口刻意不接受单价、总额、押金 ——
  凡是能换算成钱的字段,只要允许前端传入,就等于把定价权交给了浏览器。
- **状态更新的 `WHERE order_status = 期望的原状态`** 让状态迁移变成乐观锁;
  不带这个条件的话,两个请求同时点"确认接单"会双双成功、重复发两次通知。

## 信用域

- **信用分的变更收敛到一个入口**:加分来源是分散的(订单履约、收到评价、
  管理员手动调整、纠纷判罚),各自去改 `credit_score` 的话,
  "分数变了但流水没写"这类不一致迟早出现,而且没有任何一层拦得住。
  收敛到 `CreditService.adjust()` 后,加分和写流水在同一个事务里。
- **流水记 before/after 而不是只记增量**:单看 `changeScore` 无法判断
  这笔是"从 100 加到 102"还是"从 52 加到 54"。有前后值才能对账,
  也才能在数据库层面校验出"流水串了"。
- **`0%` 和"暂无数据"必须分开**:视图对没有数据的比率返回 `NULL` 而不是 0。
  一个刚注册的用户履约率显示 0%,会让他以为自己做错了什么;
  显示"暂无数据"才是事实。**这个区分只能在服务端做** ——
  前端拿到 0 是分不清"真的是 0"还是"没有数据"的。
- **匿名是"保留事实、控制展示",不是"不查"**:数据库里始终存着真实的
  `from_user_id`,纠纷处理时平台需要能追溯到人;只在返回给前端时替换姓名、
  抹掉 ID。反过来做更省事,但一旦要做"争议评价核实",数据链就断了。
- **评价的信用分影响与订单履约分开记**:一单走完是 "+2 履约" 加
  "+1 好评" 两笔独立的账。合成一笔的话,用户看到总分涨了却说不清涨在哪。
- **隐藏评价要同时改信用口径**:管理员隐藏一条差评,不只是"不显示" ——
  它会立刻从"评价均分"和"资源完好率"里消失。这正是
  `v_user_credit_summary` 视图里 `e.status = 1` 那行条件的意义。

## 互动域(站内信 / 提现 / 纠纷)

- **余额没有"简洁公式",四个数字必须分开摆**:最容易写出的恒等式是
  "余额 = 累计收入 − 累计提现",但它是**错的** —— 平台上买家自己也要付款,
  出账有付款和提现两条路径。真正的恒等式是
  `累计入账 − 累计付款 − 累计提现 = 余额`。只摆两个数,买家和卖家都会算不平。
  与其硬凑一个经不起追问的公式,不如把口径标清、把流水摆出来让用户逐笔核对 ——
  `WalletVO` 的注释里明确写了"刻意不做恒等式",这是主动的取舍而不是遗漏。
- **押金从来没有进过卖家的余额**:押金由买家支付、租完原路退回买家。
  所以"卖家把买家的押金提走"在这套账上不可能发生 ——
  **不是靠校验拦住的,而是结构上就没有这条路径**。靠校验拦的东西,
  总有一处会忘;没有那条路径,就不需要拦。
- **提现必须 `FOR UPDATE` 锁余额行**:余额 100、两个浏览器同时提 100,
  不加锁会双双通过校验、余额变 -100。这是最经典的并发 Bug,
  也是论文里"事务"那条硬指标最直观的对比测试素材。
- **状态机规则只定义一处**:能不能撤销纠纷,由后端在 `DisputeVO.canCancel`
  里算好再返回。前端自己 `if` 一遍的话,后端哪天加了"处理中不可撤销",
  界面上就会出现一个点了才报错的按钮。同理,纠纷**只能**在 2/3 状态申请这条
  规则也只写在 `BizDisputeServiceImpl` 里。
- **"已有未决纠纷"的守卫必须排在订单状态检查之前**:两条提示的分工完全不同 ——
  状态检查给出的是"订单当前状态为「纠纷中」,已付款且未完成的订单才能申请纠纷",
  用户看完不知道该干什么;而"已有正在处理的纠纷"直接告诉他等调解。
  顺序反了的话,后者永远不可达,用户只会看到前一句。
- **会话是"打开"的,不是"新建"的**:所有会话都源于资源详情页的「联系发布者」
  或订单详情页的「联系对方」,由服务端按 (双方, 资源) 复用。
  允许凭空新建的话,同一个人会在列表里出现七八次,历史消息也散成几摊。
  创建入口收在一处,是因为这条规则一旦散在多个页面,迟早有一处写成"每次都新建"。
- **敏感词的原则是"保留事实、控制展示"**:替换类词存原文、只在读取时打码,
  当事人看到 `***` 和一个「内容已过滤」标记,管理员在纠纷调解时能看到原文。
  不把过滤这件事说破,用户会以为对方打错了字,反而去追问。
- **管理员读私聊要有动作痕迹**:后台调解抽屉里的聊天记录默认折叠、
  展开才发请求 —— 不是为了省流量,而是让"管理员读过谁的私聊"这件事
  留下一个明确的动作,而不是静默地摆在页面里。
- **纠纷本身不动钱、不改信用分,必须在界面上说清**:用户很容易以为
  "提交了纠纷钱就冻结了",不说明白他会一直等一个不会来的结果。
  调解结果要退款走「强制取消订单」、要扣分走「信用分调整」。
- **撤销纠纷不收集理由**:后端的 cancel 接口不接收撤销理由
  (`PUT /dispute/{id}/cancel`,无请求体)。摆一个填了也传不上去的输入框,
  用户会以为自己写的理由被记录下来了 —— **一个假的输入框比没有输入框更坏**。
  真需要留痕,该做的是给后端加字段,而不是在前端假装有。

## 留言板与公告

- **上锁顺序定死了:先主帖行,后子行和计数。** 这是 6c 最难的一处缺陷,
  而且它不是"代码写错了",是**并发下必然发生**的死锁。
  点赞和回复都要写两处:先往子行插一条(`biz_board_like`,或 `parent_id`
  指向主帖的那条回复),再回主帖把冗余计数 +1。而"插子行"这一步会顺带在
  主帖行上加一把**共享锁** —— 外键检查要求的:要往 `board_id` 里写值,
  MySQL 得先确认被引用的那行还在。于是两个并发请求各自攥着主帖行的共享锁,
  又都想去把同一个计数 +1(需要排他锁)。共享锁之间不冲突、共享锁与排他锁
  冲突 —— 两边都在等对方先松手,环就闭合了。InnoDB 死锁日志里两边一字不差:
  `HOLDS lock mode S locks rec but not gap` + `WAITING lock_mode X locks rec but not gap`。
  表现是 5 个人同时点一条帖:2 个报"系统繁忙",计数只加到 3。
- **锁升级类的死锁只能靠顺序治,不能靠降隔离级别治。** 我一开始的直觉是
  降成 `READ COMMITTED`(那确实治好了另一个"同一个人连点"的间隙锁死锁),
  但这一处照样死 —— 已验证。降隔离级别治的是**间隙锁**那类,而这里是
  **共享锁等升排他锁**,和间隙无关。治法只有一个:事务开头就用
  `SELECT ... FOR UPDATE` 把主帖行锁住(`selectByIdForUpdate`,而不是读一把
  就走的 `selectById`),后面插子行、改计数要的锁都已经在自己手里。
  **同一个帖子上的写操作因此变成串行** —— 这个代价换来的是"锁顺序永远一致,
  环形不成",村级留言板的并发量下这笔交换划算。
- **`deleted = 0` 在手写 SQL 里必须自己写**:`@TableLogic` 只对框架生成的
  SQL 生效,`FOR UPDATE` 这条是手写的,漏了它的表现是"删掉的帖还能被点赞"。
- **层级压到两级是一道接口约束,不只是界面约定**:回复的回复会被
  `parent_id` 非空直接拒掉。层级任意深的话,列表渲染要递归、删除要处理整棵
  子树、权限要顺链路往上找;村级留言板用不到这些。真要追问某个人,
  正确做法是在回复里点名 —— 村民之间本来就这么说话。
- **冗余计数的正确性用"对账"验,不用"读回来看看"验**:E2E 的判据是
  "逐个人问一遍 `liked`,说是的人数必须等于 `like_count`"。这个判据
  **与并发落库的顺序无关**,所以它既能在单人操作下通过,也能在 5 个人同时
  点赞之后通过 —— 只断言"计数从 0 变 1"是验不出丢更新的。
- **存原文、读取时打码,和站内信是同一套做法,理由有两条 —— 第二条是预留的**:
  一是词库调整后老内容能跟着变,这一条现在就成立。
  二是**为"违规内容复核"预留的**:原文留着,将来做复核时不必让用户重打一遍。
  这一条目前还没有兑现 —— 前后台共用同一套打码口径,`maskAll` 对管理员的
  列表同样生效,**当前版本没有任何接口能把原文取出来** ——
  这一条记在 [README](../README.md) 的「待优化」一节里。
  也就是说现在兑现的是"保留事实",还没有兑现"让人能复核"。
  写成预留而不是"已经支持复核",是因为一旦论文里写了能复核,
  答辩时被要求演示一下就露馅了。
  作者本人看到的也是打码版 —— 让他看原文会更"友好",但那样同一个字段
  对不同的人返回不同内容,前端就得多知道"我是作者"这个分支,
  换来的只是省一次改字。
- **留言的「隐藏」是一个预留状态。** `biz_board.status` 的值域里有 2(已隐藏),
  前台那条 SQL 写死了 `status = 1`,所以隐藏对前台的唯一效果就是看不见;
  但**当前版本后台的处置动作只有"删除"** —— `sys_menu` 里这个菜单下
  只定义了 `board:list` 和 `board:delete`,没有"隐藏"这个码,
  接口也没有。这个状态留着是零成本的(列已经在了,前后台两条查询的口径
  也已经分开了),不做的原因是它应当和公告的「下架」一起设计:
  两者的状态语义完全相同(都是"从公开视图里撤回但保留记录"),
  分两次做必然会做出两套不一致的确认文案和两条不一致的权限码。
  公告那一侧已经按这个思路落地了(下架 + 重新发布),留言这一侧照搬即可。
- **点赞刻意不发通知。** 一条热闹的留言一晚上能被点几十下,每下推一条消息,
  用户很快就会把通知整个关掉 —— 那样真正重要的订单、纠纷通知也一起被无视了。
  通知的额度要留给需要对方采取行动的事。
- **公告的可见范围不写进 SQL 的固定条件里**,和视图那条取舍是同一个判断:
  "只看上架"对所有调用方一致,能固化;"看哪些村的公告"因角色而异
  (游客/村民/村管/超管四种口径),必须留在外层。同一个 `/announcement`
  页面、同一个组件,游客看到 1 条、村民看到 5 条、别村村民看到 1 条,
  差别全部来自 token 里的村组 —— 页面里一个村组选择器都没有。
- **读不到的公告返回 404 而不是 403,而且失败不给别人刷浏览量。**
  403 等于确认"这条公告存在",对一个跨村越权的人来说这就是信息泄露;
  自增浏览量必须排在权限校验**之后**,否则谁都能靠反复请求把别人的公告
  刷成热门 —— 一个失败的访问不该产生任何副作用。
- **公告的"系统公告"类型做了两层拦截**:前端按角色把选项过滤掉,
  后端 publish / 编辑里各判一次 403。前端隐藏挡不住直接发 HTTP 请求,
  两层都要有 —— 这和按钮级权限是同一个道理。
  **编辑这一层挡的是另一个方向**:不能让一条村级公告把类型改成 5,
  落款还是本村,看起来却像平台发的通知。
- **公告的四个写动作各有各的副作用,所以不能合成一个"保存"**:
  新建时「确认发布」要发通知、「存草稿」不发;编辑已发布的不重发通知
  (改错字不该把全村人的通知栏再刷一遍);下架不发(已经推出去的通知收不回来);
  **重新发布要发** —— 一条公告重新可见这件事本身值得再推一次,
  沉默地让它复活,村民会以为它一直是可见的。把"改内容"和"改状态"
  合成一个动作,这几个不同的副作用就无法区分了 —— 而它们的区别
  恰恰是管理员最需要被告知的一件事,所以每一个都写在按钮和确认框上。
- **「存草稿」不占一个新的权限码。** 它不是一种新的能力,只是"新建公告"
  这个动作的一个分支:一个人如果能新建公告,他就有权决定这条公告
  现在发还是晚点发。单独加一个 `announcement:draft`,权限表里只会多一条
  永远和 `add` 一起授予的记录。
- **下架必须可逆,否则后台会攒下一批谁也动不了的公告。** 所以下架之后
  那一行的按钮是「发布」而不是灰着的「下架」——"只能下架、不能重新发布"
  在设计上是个死路,而一个死路在演示时看不出来,要等到有人误点才发现。
- **编辑的三个字段(`village_id` / `publisher_id` / `status`)不进 DTO。**
  DTO 里没有的字段,前端在请求体里塞了也会被框架静默忽略 ——
  接口测试专门塞了 `villageId: 3`、`publisherId: 1`、`viewCount: 9999`
  各试一遍,断言它们在库里原封不动(批量赋值那类越权最常见的入口,
  就是"某个字段名恰好和服务端模型撞上了")。

## AI 智能客服

- **提示词不是"角色扮演",是业务规则的唯一副本。** 不给规则的时候,模型会
  用常识把问题答圆:问"租拖拉机押金怎么算",它答"押金一般由出租方按机型、
  租期协商确定,常见为租金的一定比例" —— 这句话放在任何租赁平台都成立,
  放在本平台是错的(押金是资源上一个固定字段,应付 = 租金 + 押金)。
  **这种错比"答不出来"更坏**:读起来完全合理,用户会照着它去下单,
  到支付页发现数字不一样。所以 `PromptTemplate` 里的每一条规则都能在代码里
  找到出处,而不是凭印象写的。
- **兜底答案和 AI 答案必须是同一套说法。** 不然会出现最难查的一类 bug:
  同一句话问两遍,网络好时答"应付 = 租金 + 押金",网络差时答"押金按比例算"。
  用户不知道哪个是对的,而这种不一致只有在降级路径被触发时才显形 ——
  测试里几乎撞不到。所以 `FallbackFaq` 的每一条都是从提示词里那句话抄过来的,
  两者放在同一个包下,注释里点明了"改一处要改两处"。
- **"提问被拦下"和"AI 调不通"是两件事,不能合成一个失败。**
  前者压根没出网(不花钱、也没把违规内容送给第三方),后者是服务可用性问题。
  所以前者记 `status=3`、模型列写 `(未调用)`、token 和耗时都是 0 ——
  这几样合起来是"没出网"的可验证证据。混成一条的话,
  后台的降级率会把"有人试图问违规内容"算成"AI 挂了",排查方向直接被带偏。
- **出口的内容安全只拦不替换,和留言板、站内信不一样。** 那两处打码是因为
  "内容是用户写的,要保留事实以便复核";AI 的回答不是证据,它只是一个
  即时生成的回复。把里面几个词打成星号,换来的是一段用户读不通的话。
- **模型名写错是不会报错的。** 实测传一个已退役的模型名(`deepseek-chat`),
  接口返回 200,而且响应体里的 `model` 被换成了 `deepseek-flash` ——
  服务端静默回退到默认模型。也就是说"配错了模型"既不会报错、也不会体现在
  结果里。所以启动时把生效模型打进日志,自检接口(`/api/ping/ai`)还会拿
  `GET /models` 的清单和配置值对一下,专门抓这个。
- **`/api/ping/ai` 自检为什么不发一句真话去试。** 它在免登录白名单里,
  发真话等于把烧额度的开关摆给所有人。所以走免费的 `GET /models`:
  既证明了密钥和网络通,又能查出"配的模型服务端认不认"。
  另外这个接口**失败也不抛异常** —— 诊断接口的职责是把原因说清楚,
  它自己变成 500 就什么都没说明白。
- **`sessionId` 由前端生成,所以它不可信。** 取多轮上下文时只按
  `session_id` 查是个实打实的漏洞:把自己的 sessionId 改成别人的,
  下一句提问就会带着别人的历史一起发给模型,模型的回答里很可能
  顺着上下文复述出来。所以取历史必须**连归属人一起验**。
- **`@Transactional` 不能加在这一层。** 一次问答里有最长 10 秒的外部调用,
  把它放进事务等于让一个数据库连接陪着等 10 秒 —— 连接池是有限的
  (HikariCP 20 个),几十个人同时提问就能占满,然后全站所有接口一起挂。
  这里只有一条 insert,它自己就是原子的。(整个项目里"绝不能进事务"的
  第二处是文件上传。)
- **降级路径用故障注入来验,不用"改配置重启"。** 代码正确的时候 AI 不会调不通,
  想让它调不通只能改超时或改密钥再重启 —— 那样测的是"改过配置的那一份",
  而且每条都要重启一次、进不了回归。所以照批次 5 为"事务中途失败"做的
  同一套机制,加了 `AiFailPoint`:超管装载、一次性、走**和真实失败完全相同**
  的代码路径。这直接对应验收项 AI-02 / AI-03,而它们原本是被归为
  "手工验证"的。

## 智能推荐(含资源收藏)

- **浏览由前端上报,其余四种行为在服务端记。** 收藏、下单、评价在服务端
  **必然发生**(不写库就做不成),顺手记一笔最可靠;而浏览不一样 ——
  后端只知道"详情接口被调了一次",不知道用户在这页待了多久、是从哪儿点进来的,
  而这两样正是推荐算法和推荐位点击率需要的。**分工的依据不是"哪边方便",
  而是"谁真的知道这件事"。** 代价是前端不报就没有记录。
- **上报要挂三个触发点,只挂一个会漏。** 这条是实测踩出来的:第一版只用
  `onBeforeUnmount`,而它**只在 SPA 路由切换时触发** —— 整页跳转、
  在地址栏敲另一个网址、关标签页都不会走它。E2E 里"点推荐卡片 → 点链接离开"
  那次点击就永远丢了。补上 `pagehide` 与 `visibilitychange`,并且改用
  原生 `fetch(keepalive: true)`(只有它能带 keepalive,普通请求在页面
  销毁时会被浏览器掐掉)。**这不是优化,是"报得出去"和"报不出去"的区别。**
- **采集这一层永远不抛异常。** 它是旁路:用户来看资源、下单、评价是主流程,
  而"记一笔他看过什么"是附加动作。一次 insert 失败绝不该让主流程失败 ——
  用户因为"行为记录写不进去"而下不了单,是荒谬的。
  这不是"静默吞异常"那种坏味道:日志里留了痕,而且就算采集全挂,
  系统也只是推荐变笨,功能本身不受影响。**旁路就该有旁路的失败姿态。**
- **游客不采集,而且这不是妥协。** `user_id` 是非空外键本来就存不下匿名行为,
  但更主要的理由是隐私:没登录的人只是在看,平台没有理由把他的浏览
  记下来并据此给他画像。顺带一个好处 —— 曝光和点击都只在登录时记录,
  所以后台那个点击率天然是"登录用户的",不需要额外解释为什么游客不算。
- **行为的分类字段由服务端查,不接受前端传。** 两个理由:推荐算法的输入
  不能是客户端说了算的(伪造一个分类就能把推荐往别的方向带);以及分类会被改,
  而行为记录至少应当反映一个权威值。
- **推荐理由说「关注过」而不是「看过」。** 一条分类偏好可以来自五种行为里的
  任何一种。只下过单、从没点开过详情的用户被告知"你看过「电动车」",
  那是编的 —— 而**推荐理由的全部价值就在于它说的是真的**。
  第一版写的就是"你看过",写测试时才发现一个下单驱动的偏好会被它描述错。
- **冷启动不编理由,标题也跟着变。** 没有行为的用户拿到的是本村热门,
  理由是「本村热门」/「大家都在看」,不是"根据你的兴趣";首页那一块的标题
  也从「猜你喜欢」变成「热门推荐」。**对一个我们一无所知的人假装了解他,
  是推荐系统最容易露馅的地方。**
- **三路召回按顺序补位,而不是加权融合。** 内容推荐 > 村组热度 > 全局兜底。
  加权融合看起来更"高级",但它的代价是**解释不清**:一条结果由三路各贡献
  多少分,答辩时说不明白,用户也看不出理由。按顺序补位的好处是每条结果
  都能归到一个明确的来源,理由也就写得实。
- **缓存必须配主动失效,光有 TTL 不够。** 用户点开一台拖拉机、看完回到首页,
  如果推荐还在缓存里,他会看到和刚才一模一样的一批 ——
  **"我明明刚看过,它却像没看见"是最容易被察觉的算法故障**,
  比"推荐得不那么准"严重得多。所以每写一条行为就失效这个用户的缓存
  (失效很便宜,算一次推荐很贵,宁可变笨也要失效)。
- **收藏列表直接查基表,不查视图。** 视图 `v_resource_list` 把
  "只看已上架"写死在定义里(它在批次 1 就是为前台列表设计的)。
  沿用它的话,收藏过的资源一旦下架、售出或被驳回就会从收藏列表里
  **静默消失**,用户只会觉得"平台把我的收藏弄丢了"。
  所以收藏列表查 `biz_resource` 并带上状态,下架的显示成灰色卡片 ——
  **"东西没了"和"东西被系统藏了"是两件事,用户需要知道是哪一件。**
- **取消收藏要先于收藏判定。** 服务里那个 `DELETE` 必须排在
  "资源是否已上架"的检查之前,理由不是性能:用户收藏了一个东西、
  后来它下架了,那条收藏仍然挂在他的列表里,他得能把它清掉。
  顺序反了的话,这些收藏就永远删不掉 —— 界面上是一个点不动的取消按钮。
- **推荐位点击率的分母是曝光,而曝光要有专门的记录。** 只有点击数的话,
  那个数字什么都说明不了(一天 50 次点击是多还是少?)。所以加了第六种行为
  `推荐位曝光`,`点击率 = 点击 ÷ 曝光`。顺带一条:**采样粒度是一次请求一行**,
  不是每个卡片一行 —— 同一时刻同一个推荐位上十几个卡片的信息量是一样的。
- **"行为采集量"这一块和点击率并排。** 它回答的不是"推得准不准",
  而是"我们到底知不知道用户干了什么"。**推荐变笨通常不报错** ——
  某个行为忘了记、埋点断了,表现只是"不那么准了";而采集量掉到 0 看得见。
  它同时也是这一批唯一能从 HTTP 层验证"行为有没有落库"的地方
  (那几张表没有对外接口,也不该有)。
- **`favorite_count` 那一列从"恒为 0 的装饰"变成了真实的计数,要求也跟着变了。**
  同理还有 `view_count`:原来详情页的浏览量是"读出来加一再写回",
  并发下会丢更新 —— 它当时只是个装饰品,错了也没人看得出;
  但村组热度推荐**直接按 `view_count` 排序**,它变成了喂给算法的输入,
  偏小会把真正热门的资源排到后面,而那种错在界面上完全看不出来。
  **同一个字段,当了算法的输入之后就得按数据的标准要求它。**

## 数据统计与操作日志

- **利用率必须用汇总后的两个数重新算,不能把各村的比率平均。**
  `StatServiceImpl.overview` 里是 `(使用中 + 已完成) ÷ 资源总数`。
  按村平均看着更"公平",实际是错的:一个只有 1 个资源、恰好成过 1 单的村
  利用率是 100%,把它平均进去会显著拉高整体。而这是个**不报错、不崩溃,
  只是数字悄悄不对**的错误 —— 而它是要写进公示页和论文的那个数。
- **村管传上来的 `villageId` 一律忽略。** 范围只由登录态决定,参数只对超管
  有意义。查询接口上"前端传什么就往后端塞"等于没有权限 —— 改一下 URL 里的
  村组 id 就能看别村的数字。这条有对应的接口用例:村管硬传 `villageId=4`
  拿到的仍是自己村的数。
- **超管打开村级统计时,默认挑一个资源最多的村。** 超管的 `village_id` 指向
  镇节点,而资源挂在村上 —— 不给默认值的话他一进来就是整屏的 0,
  看起来像功能坏了。给一个"有内容的"默认值比给一个空页面有用。
- **全局统计在 Service 里又判了一次超管**,尽管接口上已经有
  `@RequiresPerm("stat:global")`。理由:权限码是**配出来的**,后台能改。
  这个接口的语义是"全平台",哪天有人手滑把 `stat:global` 授给村管,
  他看到的不是本村,而是**所有村的横向对比**。改配置就能泄露的路径,
  值得多用一行代码钉死。
- **统计不加事务。** 一次统计跑四条查询,只读、也不追求强一致(统计本来
  就允许读到"上一秒的"数据)。包在一个事务里会把它们绑成同一个快照,
  对统计没有额外价值,却要一直占着一条数据库连接。
- **订单状态的中文名在 Java 侧翻译,不写进 SQL。** `translateOrderStatus`
  拿状态码去问 `OrderStatusEnum`。在 SQL 里写 `CASE WHEN` 等于把状态机
  定义了第二遍,两份迟早漂开(新增状态时最容易漏改 SQL 那份)。
- **状态码不在枚举里时保留原码,而不是丢掉这条。** 图上显示 `99` 总比少
  一根柱子强,而且那个数字本身就是排查的线索。
- **趋势图封顶 30 天。** 村级规模下更长的区间里大部分点是 0,
  折线会变成一根趴在底部的线,什么也说明不了。

- **操作日志:失败也要记。** 只记成功的话,"有人反复尝试越权删除"在日志里
  完全看不到 —— 而失败的尝试恰恰最该被看见。`status` 因此有两档,
  失败的还记下异常信息。有测试专门造一次失败(编辑一条不存在的公告)
  再回头确认那笔 `status=0`。
- **异常只存类名 + 消息,不存堆栈。** 堆栈进审计表会把表撑爆,
  而审计要回答的是"谁在什么时候做了什么",不是"代码在哪一行炸的"。
- **日志写不进去绝不能影响业务。** 和 AI 行为采集同一条原则:旁路就该有
  旁路的失败姿态。insert 包在 try 里,失败只留一行 warn。
- **密码、身份证必须脱敏,而且要递归。** `sys_operation_log.params` 是
  "很多人能看"的表,明文密码躺在这里比泄露在别处更糟 —— 登录、注册改密、
  实名提交都会经过这个切面。**递归是必须的**:只处理第一层的话,
  一个 `{"user": {"password": "..."}}` 就绕过去了。
- **参数要截断(1000 字符)。** 有人往备注里粘一万字,日志表就多一条巨长的
  记录。审计要的是"能看懂发生了什么",不是"完整复刻请求体"。
- **客户端 IP 取 `X-Forwarded-For` 的第一个,而不是 `getRemoteAddr()`。**
  这一条是被批次 9 的部署逼出来的:上了 Nginx 之后,`getRemoteAddr()` 拿到的
  是 **Nginx 容器的内网地址**(172.x),每个请求都一样,审计价值直接归零。
  必须靠 Nginx 的 `proxy_set_header` 把真实 IP 带过来。
- **操作人存的是显示名而不是手机号明文。** 实名优先(村里认人),
  未实名退化成 `138****0000`。审计能认出是谁就够了,存明文没必要。
- **写死的日期是一种会自己烂掉的断言。** `api_test_stat.py` 里有一条验
  "日期区间选今天能查到今天的日志、结束日期含当天",第一版把日期**写死成
  写脚本那天的日期**。当天跑是全绿的,第二天再跑就挂了 —— 它筛的仍是前一天,
  拿到的条数和"全部"对不上,而**失败信息看起来像产品坏了**
  (报的是"今天 25 条 vs 全部 133 条"),排查方向直接被带偏。
  修法有两步,缺一不可:① 日期改成 `datetime.now()` 算出来;
  ② 判据改成**只看这次查询本身对不对**(查到的每一条 `createTime` 都是今天),
  不再依赖"库里恰好只有今天的日志"这个会随时间漂移的隐含前提。
  **顺带**:`05_mock_data.sql` 也补上了 `sys_operation_log` 的清理 ——
  它和 `ai_chat_record` 一样是只增不改的表,不清的话每跑一轮就攒几十条,
  而"重置演示数据"的意义就是回到一个已知状态。**补一个更聪明的断言,
  不如让前提真的成立**;两件都做了才算修干净。

## 容器化部署

- **只有 frontend 暴露端口。** 浏览器只访问一个地址,跨域问题从结构上不
  存在(而不是靠后端配 CORS 放行);后端不映射端口意味着它不可能被绕过
  Nginx 直接访问。**网络层的收紧比在代码里判断来源可靠。**
- **Nginx 反代而不是前端写死后端地址。** axios 的 `baseURL` 从头到尾都是
  相对的 `/api`,开发期由 Vite 的 proxy 转发,生产期换成 Nginx ——
  **前端代码一个字都不用改**。反过来写死 `http://后端IP:8080/api` 的话,
  要处理跨域、要把后端端口暴露到公网、换台机器就要重新打包,
  三个问题一起冒出来。
- **`proxy_pass http://backend:8080;` 结尾不能加斜杠。** 加了会把 `/api`
  前缀截掉,后端全部 404 —— 而且报错是"接口不存在",不会有人往 Nginx
  配置上想。
- **必须让后端从 `X-Forwarded-*` 还原真实来源,否则同源 POST 会被当成跨域。**
  这是这一批抓到的最隐蔽的一个 bug,单独展开:

  **现象**:部署完之后首页能打开、资源列表也有数据,但**一登录就失败**。
  浏览器控制台里是 `403 Invalid CORS request`,页面停在登录页没有任何提示。

  **原因**:前端和服务端都在同一个 Nginx 后面,浏览器发的是同源请求,
  本来根本不该有 CORS 检查。但**浏览器对 POST 会带 `Origin` 头**(GET 不带),
  而 Spring 的 `CorsUtils` 判断跨域时,拿 Origin 和"请求自己"比 ——
  后端只看得见自己监听的是 `http://localhost:8080`,Origin 写的是
  `http://localhost:8088`,端口对不上就判定成跨域;8088 又不在
  `allowed-origins` 里,于是直接 403。

  **为什么难发现**:GET 请求不带 Origin,所以**列表、详情、首页全都正常**,
  只有登录、下单、发布这类**写操作**全军覆没。这个形态看起来像
  "后端接口挂了"或者"用户密码不对",排查方向完全被带偏 ——
  而实际上后端好好的,是它自己把同源请求当成了外来的。

  **修法**:`server.forward-headers-strategy: framework` + Nginx 注入
  `X-Forwarded-Proto` / `-Host` / `-Port`。还原之后后端看到的来源和
  Origin 一致,同源成立,CORS 检查自然不触发。

  **这里还埋着第二个坑**:`X-Forwarded-Port` **不能直接用 `$server_port`**。
  容器里的 Nginx 监听的是 80,宿主机把它映射成 8088,而 `$server_port`
  永远是 80 —— 用了它后端仍然算出 `80 ≠ 8088`,修了等于没修。
  端口要从 `$http_host`(形如 `localhost:8088`)尾部抠出来,见
  `docker/nginx.conf` 里那个 `map`。

  **回归方式**:`e2e/deploy.mjs` 里留了两条断言 —— 一条要求"带 Origin 的
  同源 POST 必须通过",一条要求"`Origin: http://evil.example` 仍然返回 403"。
  两条都要有:修这类问题很容易顺手把 CORS 整个放开,那就从"登录不了"
  变成了"谁都能调"。**只留第一条的话,把 CORS 关掉也能让它变绿。**
- **`client_max_body_size` 必须改(默认 1MB)。** 不改的话传图片得到 413,
  而前端拿不到后端的错误信息,看起来就是"上传按钮没反应"。
- **`proxy_read_timeout` 给到 120 秒,远宽于后端 AI 的 10 秒。**
  Nginx 先超时的话用户看到的是 502,而不是后端那句"AI 暂时不可用,
  以下是常见问题解答" —— **三级降级就白写了**。
- **`try_files $uri $uri/ /index.html` 是 history 模式的必需品。**
  前端路由的 URL 在服务器上没有对应文件,用户按 F5 就是 404。
  开发期不会遇到这个问题(Vite dev server 自带回落),
  所以"开发时好好的、部署后一刷新就 404"是个经典现象。
- **镜像里必须删掉 `application-dev.yml`。** 那个文件被 `.gitignore` 挡着,
  仓库里没有 —— **但 `docker build` 的上下文是工作目录,不是 git 的索引**,
  untracked 的文件照样会被 COPY 进去。不删的话密钥就固化进镜像层,
  推到哪跟到哪,`docker history` 还能翻出来。`.dockerignore` 里另挡了一道:
  两个不同的保护面,不是一个的备份。
- **部署配置全部走环境变量,不新增 profile 文件。** `application.yml` 里
  原本就写了 `${DEEPSEEK_API_KEY:}`;Spring Boot 的加载顺序里
  **环境变量优先于 application.yml**,所以 `SPRING_DATASOURCE_URL`、
  `APP_UPLOAD_PATH` 这些直接生效,代码一行不用改。
- **两阶段构建。** 编译要 JDK + Maven(700MB 上下),运行只要一个 JRE;
  单阶段的话最终镜像会带着整套 Maven 和源码。第二阶段只 COPY 一个 jar,
  `—from=build` 之外的东西全部丢掉。
- **MySQL 的 healthcheck 用 `mysqladmin ping` 而不是 TCP 探测。**
  端口通了不等于能连 —— 初始化脚本还在跑的时候端口就已经开着。
  配合 `depends_on: condition: service_healthy`:只写 `service_started`
  的话,Spring Boot 会在 MySQL 还在跑脚本时就尝试连库,重试几次失败后
  容器退出,表现是"第一次 up 必失败,再 up 一次就好了",很难归因。
- **上传目录必须挂 volume。** 不挂的话容器一重建 `/app/upload` 就空了,
  而数据库里那些 `/upload/xxx.jpg` 的引用还在,页面全是裂图。
- **`.dockerignore` 和 `.gitignore` 是两回事。** git 管"哪些文件进仓库",
  它管"哪些文件进构建上下文"。不配的话 `node_modules`(242MB)和
  `m2repo`(72MB)每次构建都要传给守护进程,白等一分多钟 ——
  而这两样在容器里本来就要重新装。

**国内拉镜像的实测记录(部署这一批踩得最久的一件事):**

- Docker Hub 直连不通(`registry-1.docker.io` 超时)。配了加速源之后,
  `docker.m.daocloud.io` 和 `docker.1ms.run` **能取到 manifest,但 blob
  下载会卡在 0% 不动** —— 表现是 `docker pull` 输出停在 "Pulling fs layer"
  之后毫无进展,而且不报错、不超时,看起来像网络慢。
- 最终可用的是**华为云 SWR 的完整路径**:`swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io/library/<镜像>`。
  拉下来之后 `docker tag` 回标准名,compose 文件里仍然写 `mysql:8.0`
  这种干净的名字,不用把这一长串泄漏到交付物里。
- `maven:3.9-eclipse-temurin-17` 这个精确 tag 在国内几个源上都是 404,
  能取到的只有浮动的 `maven:3-eclipse-temurin-17`(当前解析到 3.9.9)。
  本项目要求 Maven ≥ 3.6.3,大版本 3 之内都满足;要严格锁版本应当换成
  `maven@sha256:...` 的形式。

## 这份文档的维护约定

**"为什么这么做"写到这里,不要写回 README。**

README 是入口 —— 它要回答的是"这东西怎么跑、能做什么、验到什么程度",
读者多半是第一次接触这个项目的人,或者隔了几天回来的自己。
而取舍是**深水区**:只有准备答辩、或者准备改这块代码的人才会读。
两类内容混在一个文件里,结果是两边都不好用 —— 想找启动命令的人
要翻过两百行"为什么",想通读取舍的人又得在命令和截图里找。

**新增一条取舍时:**

1. 先判断它属于哪个域,加到对应的小节里(域不够用就新开一个 `##`)。
   按域组织而不是按批次,是因为**读的人按"我要改哪块"来找,
   而不是按"这是哪一批做的"**。
2. 一条写成**「做法 + 为什么 + 不这么做会怎样」**三段里的至少两段。
   只写"我们用了 X"没有价值 —— 那是代码就能看出来的东西;
   要写的是"为什么不是 Y",那才是答辩会问的。
3. **踩过的坑优先写。** 那些"实测发现""连跑十几轮才撞到一次"的记录,
   比任何设计原则都有说服力 —— 它们证明这件事是被验证过的,
   而不是被想出来的。
4. 涉及具体代码的,把文件名或方法名带上(写成 `` `类名.方法名` ``),
   方便顺着去读实现。但**不要把代码贴过来** —— 代码会变,贴过来就会过期。

**什么时候该删:** 如果某条取舍背后的实现被改掉了,而这条没跟着改,
那它就从"论证"变成了"误导"。改代码时顺手扫一眼这里有没有对应的条目 ——
这一条适用于这份文档里的每一节,包括上面那些已经写完的。
